October 2026

I’m trying to get better at finishing things

I have more ideas than finished projects sometimes. I’m learning that choosing one thing and taking it to a usable version is its own skill.

↘
I like exploring ideas. One minute it’s a data project, the next it’s an AI tool or a small app that solves an everyday problem. That curiosity is useful, but it can also pull me in too many directions. I’m trying to put more value on finishing: making the basic version work, testing it, fixing what breaks, and letting someone else use it. A project doesn’t become better just because the idea behind it is ambitious. It becomes better when the details are handled and the thing actually works.
September 2026

Learning a tool isn’t the same as knowing what to do with it

Knowing Python or SQL syntax is one thing. Knowing which question to ask, and how to check the answer, is another.

↘
It’s easy to measure progress by how many topics or libraries I’ve covered. But when I work on an analysis, the harder part is often deciding what I actually need to find out. Python can clean and transform data; SQL can help me pull the right rows; a chart can make a pattern easier to see. None of those tools can rescue a question that hasn’t been thought through. I want to get more comfortable explaining why I used a method, what the result means, and what it still doesn’t tell me.
August 2026

QPGen made the gap between an idea and a product feel real

A working feature involves more than the part people see. There’s authentication, data, errors, and a lot of small decisions in between.

↘
With QPGen, the idea of generating question papers with AI was only the starting point. Turning that idea into an application meant thinking about the API, the database, user authentication, and how the different pieces fit together. Those parts aren’t as exciting to describe as the main feature, but they’re what make a project usable beyond a quick demo. It changed how I look at software: the visible feature is only one part of the work, and the unglamorous details deserve attention too.
July 2026

Messy data is usually where the real work starts

Missing values, inconsistent labels, and awkward formats are not side quests. They’re often the first thing an analysis asks you to understand.

↘
A dataset can look ready to analyse until I start checking it closely. Then there are duplicates, empty fields, inconsistent categories, or values that don’t make sense together. It’s tempting to clean everything quickly and move on to the charts, but those decisions can change the result. I’m learning to pause and ask what a missing value means, whether two labels really refer to the same thing, and what I might lose by removing a row. Good analysis starts with understanding the data, not decorating it.
June 2026

Debugging is a lesson in being less attached to my first guess

When something breaks, my first explanation is only a hypothesis. The useful part is checking it instead of defending it.

↘
I’ve learned that staring at a bug and hoping the answer appears is not much of a debugging strategy. It helps more to narrow the problem down: reproduce it, read the error, check the inputs, and change one thing at a time. Sometimes the issue is much smaller than I imagined; sometimes my understanding of the code was wrong. Neither is a disaster. I’d rather learn to investigate calmly than pretend I should get everything right on the first attempt.
May 2026

I don’t need my entire career figured out before I start

I’m interested in data, Python, and building useful software. For now, doing the work is a better way to learn what fits than overthinking every possible path.

↘
I’ve spent time wondering which role I should aim for and which skills I should prioritise. Data analytics interests me because it combines problem-solving with making sense of information. Python also gives me a way to automate tasks and build things, while projects expose me to the engineering behind an idea. I don’t think I need to choose a permanent label for myself right now. I need a solid foundation, projects I can explain honestly, and enough experience to make the next decision with better information.
April 2026

Consistency looks less impressive than a fresh start

Making a perfect plan feels productive. Coming back to the same skill and practising it again is what actually builds familiarity.

↘
I can spend too much time organising what I’m going to learn: the roadmap, the resources, the order of topics. Planning has its place, but it can become a comfortable substitute for doing the work. With Python and SQL, I need to write queries, solve small problems, make mistakes, and return to concepts I’ve forgotten. I’m trying to care less about having the perfect routine and more about making steady progress I can actually sustain.
March 2026

A chart is not the same thing as an insight

A visual can make a result look convincing. I still need to know what it shows, what could explain it, and what it leaves out.

↘
Data analytics can make it tempting to jump straight from a dataset to a dashboard. But a clean chart is only useful if it answers a real question. I want to get better at looking beyond the obvious pattern, checking whether the comparison is fair, and being clear about uncertainty. Sometimes the honest conclusion is that the data isn’t enough to support a strong claim. That might sound less impressive, but it’s more useful than pretending the chart says more than it does.
February 2026

AI is useful, but I still want to understand what I’m building

Getting an AI feature to work is exciting. Being able to explain its limits and handle what happens around it matters just as much.

↘
AI tools make it easier to experiment with ideas that once felt out of reach. But adding an API call doesn’t automatically make an application thoughtful or reliable. I still need to understand the inputs and outputs, handle failures, think about the user experience, and check whether the result is actually useful. I don’t want to use AI just because it sounds impressive in a project description. I want to understand where it helps, where it can go wrong, and what the rest of the software needs to do around it.
